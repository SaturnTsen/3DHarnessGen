# Blender 9B 长序列显存估算与优化建议

基于本地 Qwen3.5-9B 配置、在 meta 设备上构造的模型结构和最长样本 OOM 结果计算；未加载权重或再次训练，未修改正式配置。计算脚本和数值保存在 `temp/blender_memory_theory/`。

## 计算条件

每卡微批次 B=1，最长输入 S=90526，隐藏维度 H=4096，前馈中间维度 I=12288，文本层数 L=32（24 层线性注意力、8 层完整注意力），词表 V=248320。计算中的 GiB 均为字节数除以 2^30。BF16 张量按每元素 2 字节计；归一化等局部计算可能使用 FP32。

## 静态状态

meta 模型参数总数 9409813744。按线性层转换为 4-bit、排除 lm_head 的规则，量化参数约 7369682944，其他参数约 2040130800。后者包括不共享的输入 embedding 与 lm_head，各 1017118720 参数。当前 PEFT k-bit 准备逻辑将非 Params4bit 的半精度参数转换为 FP32。

理想双卡均匀分片静态预算：

`(7369682944 × 0.5 + 2040130800 × 4) / 2 / 2^30 = 5.52 GiB/卡`

这不包括量化元数据、FSDP 临时聚合/精度转换、缓冲区与 CUDA/NCCL 工作空间，不能视为实际加载后显存。

当前视觉冻结，LoRA 只匹配 8 个完整注意力层的 q/k/v/o 投影，共 3932160 参数。按 FP32 参数、梯度和两个 Adam 状态合计 16 字节/参数、双卡完全分片，约 0.0293 GiB/卡。即使全部复制也只约 0.0586 GiB；优化器不是主要矛盾。

## 激活张量量级

| 张量或存量估算 | S=90526 | S=163840 |
| --- | --- | --- |
| 一份 BF16 hidden `[1,S,4096]` | 0.691 GiB | 1.250 GiB |
| 32 个层边界，各一份 BF16 hidden | 22.10 GiB | 40.00 GiB |
| 29 个层边界，各一份 BF16 hidden | 20.03 GiB | 36.25 GiB |
| 一份 BF16 MLP 中间张量 `[1,S,12288]` | 2.072 GiB | 3.750 GiB |
| 一份 BF16 query+gate `[1,S,8192]` | 1.381 GiB | 2.500 GiB |
| 一份 FP32 query `[1,S,4096]` | 1.381 GiB | 2.500 GiB |
| 一份 BF16 key 或 value `[1,S,1024]` | 0.173 GiB | 0.313 GiB |
| 未分块的 BF16 logits `[1,S,248320]` | 41.87 GiB | 75.78 GiB |

层边界表是按每层存一份独立 BF16 输入的数量级估算，不是实际张量生命周期计数。LoRA 首次出现于第 4 层，此前冻结层通常不需要反传，29 层口径用于展示这种影响；共享存储、精度、检查点实现和引用存活会改变实际值。若相同存量是 FP32，字节数翻倍。不能把表中所有项目相加当作精确峰值。

当前 `chunked_nll` 已避免完整 logits：本地实现每块 256 个 token，一块 FP32 logits 约 0.237 GiB，但损失计算还有其他张量，不能把 0.237 GiB 当作总损失显存。当前目标 token 占绝大多数，仅跳过 prompt 不会带来数量级改善。

朴素完整注意力的单层 BF16 分数矩阵 `[1,16,S,S]` 为 244.23 GiB，S=163840 时为 800 GiB。当前 SDPA 前向成功，说明没有按该朴素方式同时物化完整矩阵；这些数值不能计入当前实际峰值。

因此 S=90526 时，仅静态分片与层边界的示意预算就约 25.5–27.6 GiB/卡，随后还需当前层的若干 GiB 张量、反向梯度、FSDP 聚合及工作空间。实测 rank 1 已分配峰值 44.62 GiB、保留峰值 46.91 GiB，并在反向重计算的 LoRA 输出投影失败。该结果与激活主导的判断一致，但不是各组成项的实测分解。

不能从一次失败准确推导成功运行所需总显存或“只差多少”：失败时的待申请块不是后续全部需求。S=163840 相比最长真实样本为 1.81 倍；层边界存量估算单独就达 36.25–40 GiB/卡，容量压力更大。当前 max_length 只是拒绝阈值，不会预分配至该长度。

## 梯度检查点为什么不足

逐层检查点丢弃层内部多数反向所需中间张量，保留层输入，在反向时重新计算。它没有消除保存的层输入，也没有让当前层计算变成零显存；反向阶段会同时存在尚未释放的检查点、重计算中间张量和梯度。本次堆栈正位于该重计算阶段。

FSDP 分片模型参数、梯度与优化器状态，不会自动按序列切分样本激活。两卡各处理完整序列；增加 FSDP 卡数通常不能按卡数降低这部分激活。冻结基础权重仍需通过这些层传播梯度到较早 LoRA 模块。

## 建议顺序

1. **激活卸载**：首先试 `method.backend.activation_offloading=true`，保留检查点，将保存的激活移到 CPU，需要时回传。目标是约二十 GiB/卡级别的保存激活；并不保证全部都能卸载或最终成功。查询时主机 RAM 总量约 125GiB、可用约 93GiB，两进程的卸载有尝试空间，须测峰值 RAM、传输开销和 FSDP 兼容行为。
2. **分配器与外部占用**：独立试 `PYTORCH_ALLOC_CONF=expandable_segments:True`，降低碎片；GPU 0 测试前已有约 2.9GiB 占用。但较空闲 GPU 1 也失败，不能将问题全部归因于桌面或碎片。不能手动终止其他进程。
3. **FSDP 原生激活检查点**：评估替换普通 gradient_checkpointing，避免反向冗余 all-gather。主要是分布式调度/通信改善，不保证省掉大部分保存的 hidden。当前 schema 将 FSDP `activation_checkpointing` 固定为 false，量化梯度检查点还有一致性校验，需要明确改实现和校验，不是直接翻 YAML 即可。
4. **更细的重计算、分块 MLP 与融合归一化**：针对 2.07GiB 的 MLP 张量、1.38GiB 的 FP32 归一化临时张量减少局部峰值；需要在支持的实现中接入并验证损失/梯度。融合不会自动消除二十 GiB 的跨层保存激活。
5. **上下文并行或更大单卡显存**：上下文并行把同一条序列跨设备拆分，直接针对激活，但当前训练入口未实现；Qwen3.5 混合 DeltaNet 与多模态位置编码需要专门支持。更大显存卡也需要重测，不能据本次错误保证某个型号一定足够。

本地已确认 FLA 与 causal-conv1d 可用，DeltaNet 实际绑定 FLA 优化实现；不要把“安装 FLA”当成尚未应用的解决方案。`flash_attn` 包未安装，但当前 SDPA 也可以使用省显存注意力内核，应先确认实际内核再判断是否值得替换。

每卡批次已为 1，降低梯度累积不能缩短单个样本的序列；减少 LoRA rank/优化器状态收益相对很小。当前样本主要是约 89648 token 的目标，减少图片也无法解决主体。截断完整脚本不符合本项目要求。
